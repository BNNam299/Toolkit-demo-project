Hướng dẫn Project Docs

Mô tả ngắn từng file template — mục đích, giá trị, sections chính, quy ước ID — để người đọc (PO, dev, AI agent) hiểu nhanh và đọc đúng thứ tự.

📱 /ios-project-docs → 7 file cấp dự án + _INDEX.md
📋 /ios-spec <feature> → 3 file cấp tính năng
💻 /ios-execute <feature> → 1 file báo cáo xác minh

Thứ tự đọc

Đọc theo sơ đồ từ trên xuống — mỗi file chỉ tham chiếu file ở phía trên nó:

📱 CẤP DỰ ÁN 1. PRD.md ← chiến lược, thị trường, monetization, KPI 2. Project_Overview.md ← kiến trúc + tóm tắt kế hoạch 3. Use_Cases.md ← câu chuyện UC + ánh xạ UC↔màn + độ ưu tiên 4. Functional_Requirements.md ← FR/NFR + tiêu chí chấp nhận EARS + quy tắc validation 5. Wireframes.md ← danh sách màn + layout ASCII theo archetype 6. UX_Flows.md ← luồng điều hướng, luồng lỗi/đang tải 7. Project_Implementation_Roadmap.md ← các giai đoạn + sơ đồ phụ thuộc 8. _INDEX.md ← manifest chỉ đường + snapshot 📋 CẤP TÍNH NĂNG (cho từng tính năng) 9. spec-requirements.md ← câu chuyện người dùng + tiêu chí chấp nhận 10. spec-design.md ← kiến trúc + components 11. spec-tasks.md ← registry task + checkpoint 💻 THỰC THI 12. verification-report.md ← ma trận ĐẠT / CẢNH_BÁO / TRƯỢT

Nhóm A — Tài liệu cấp dự án

Sinh bởi /ios-project-docs <AppName>. Mỗi file qua một cổng chất lượng (gate-prd, gate-overview, gate-uc, gate-fr, gate-wireframes, gate-flows, gate-roadmap) trước khi chuyển sang file kế tiếp.

1. PRD.md Cấp dự án

Mục đích

Tầm nhìn sản phẩm, nghiên cứu thị trường, đối thủ, phạm vi MVP, monetization, KPI.

Giá trị

  • Câu trả lời TẠI SAO xây dựng sản phẩm và đo lường thành công bằng gì
  • Là nguồn chân lý duy nhất cho pricing/monetization (§11) và giá trị mặc định cho câu hỏi mở (§14)
  • Cung cấp Bảng Bằng chứng (≥28 nguồn thật) làm đầu vào cho mọi quyết định sản phẩm

Mục chính

Tóm tắt điều hành · Mục tiêu & bối cảnh · Vấn đề người dùng · Phân tích cạnh tranh · Tầm nhìn · Phạm vi MVP/ngoài phạm vi · Yêu cầu & tính năng · Luồng người dùng · Ràng buộc kỹ thuật · Danh sách màn hình · Kiếm tiền · KPI/Phân tích · Rủi ro · Câu hỏi mở · Điều phối triển khai · Bảng bằng chứng.

IDs chính

không dùng IDtham chiếu mục

Ai đọc

PO, stakeholder, người ra quyết định "xây hay không".

Ví dụ (Calo-AI): §11 đặt pricing cho gói Premium; §14 chốt giá trị mặc định (GIẢ ĐỊNH) cho free scan/ngày, độ dài dùng thử → các FR/AC/NFR phía sau tham chiếu giá trị này.

Mục đích

3. Use_Cases.md Cấp dự án

Mục đích

Giá trị

4. Functional_Requirements.md Cấp dự án

Mục đích

WHAT hệ thống phải làm — FR/NFR với tiêu chí chấp nhận EARS, quy tắc validation, xử lý lỗi.

Giá trị

  • Câu trả lời HỆ THỐNG PHẢI LÀM GÌ — cầu nối giữa UC và Design/Code
  • Mỗi FR có AC testable + độ ưu tiên + traceability ngược về UC → "no behavior without acceptance criteria"
  • Ma trận hành vi component (§2 bis) + Hành vi phụ thuộc ngữ cảnh (§2 ter) — chống FR đa màn bị xử lý tệ
  • NFR đo được (Hiệu năng, Bảo mật, Khả dụng, Độ tin cậy, Khả năng mở rộng) — không có "nhanh/bảo mật" mơ hồ

Mục chính

Giới thiệu · Yêu cầu chức năng (theo nhóm tính năng) · Ma trận hành vi component · Hành vi theo ngữ cảnh · Yêu cầu phi chức năng · Tóm tắt yêu cầu.

IDs chính

FR-XXXNFR-XXXBR-XXX.YVR-XXX.YERR-XXX.YAC-XXX.Y

Ai đọc

Dev, QA, AI agent viết design/tasks/tests.

Ví dụ (Calo-AI): FR-004 (Nhận diện món ăn từ ảnh) → AC-004.1 (happy path) + AC-004.2 (low confidence → fallback) + ERR-004.1 (network timeout); mỗi FR có 1 NFR-PERF-001 tương ứng (≤3s).

9. spec-requirements.md Cấp tính năng

Mục đích

Câu chuyện người dùng + tiêu chí chấp nhận EARS cho 1 tính năng — cầu nối giữa FR cấp dự án và Design cấp tính năng.

Giá trị

  • Mỗi AC có traceability ngược về FR-XXX + UC-XXX → biết requirement này phục vụ yêu cầu nào
  • Tham chiếu bằng chứng — chỉ ra dữ liệu thị trường, KPI liên quan từ PRD → đảm bảo yêu cầu không "trên trời"
  • Định dạng EARS (Cú pháp yêu cầu dễ tiếp cận) — WHEN/IF/THEN/WHERE — testable rõ ràng

Mục chính

Tổng quan · Tham chiếu bằng chứng · Yêu cầu (mỗi yêu cầu: câu chuyện người dùng + ACs + nguồn + độ ưu tiên).

IDs chính

AC-XXX.YAF-XXX.YFR-XXXUC-XXX

Ai đọc

Dev, QA, AI agent viết design/tasks.

Ví dụ (Calo-AI Spec-auth): Requirement "Đăng nhập bằng Apple" → AC-001.1 (happy) + AC-001.2 (user cancel) + AF-001.1 (lỗi mạng); nguồn FR-001, UC-001.
10. spec-design.md Cấp tính năng

Mục đích

Kiến trúc chi tiết cho 1 tính năng — components, interfaces, data flow, AC coverage.

Giá trị

  • "Xương" file SwiftUI — dev đọc xong biết cần tạo file nào, ViewModel nào, Service nào
  • Tóm tắt phủ AC — liệt kê AC nào được giải quyết, AC nào chưa → chống sót
  • 4 trạng thái cho mỗi tính năng (Đang tải/Trống/Lỗi/Thành công) + Trợ năng & giao diện — UX sàn
  • Ranh giới module + luồng dữ liệu → biết module nào chạm vào đâu

Mục chính

Tổng quan · Kiến trúc · Components và Interfaces · Mô hình dữ liệu · Luồng dữ liệu · Xử lý lỗi · Hành vi theo trạng thái (4 state + trợ năng) · Chiến lược kiểm thử.

Ai đọc

11. spec-tasks.md Cấp tính năng

Mục đích

Registry task máy có thể đọc + Phase gates — danh sách task cần làm, checkpoint để xác minh.

Giá trị

  • Mỗi task có Refs AC + Refs Design + Files + Checkpoint → AI agent viết code theo đúng task nào, xác minh bằng checkpoint nào
  • Phase Gates (Gate 2/3/4) — chạy XcodeBuildMCP build_sim + kiểm tra truy vết trước khi sang phase tiếp theo
  • PBT (Property-Based Testing) bắt buộc cho mỗi Tính chất đúng đắn — không phải tùy chọn

Mục chính

Chế độ thực thi · Registry task (bảng) · Phase Gates · Checkpoints · Câu hỏi mở.
