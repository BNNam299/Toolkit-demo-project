# testing-integration - Requirements

## Overview
`testing-integration` là spec cuối của Phase 9 (Polish & QA). Nó chốt chất lượng tổng thể trước khi submit App Store: (1) **E2E test** cho core loop "Camera → AI → Confirmation → Diary" chạy trên sim/device, (2) **E2E test** cho luồng subscription purchase (paywall → StoreKit sandbox → trial start → restore purchases), (3) **unit-test coverage gate ≥60%** trên core Services + ViewModels (NFR-SF-006 / Overview §6.1), (4) **App Store submission prep** — Privacy Nutrition Label, metadata App Store Connect, screenshot set đúng device class, (5) **crash-free verification ≥99%** (PRD §9 / NFR-015) đo từ Firebase Crashlytics từ TestFlight build. Spec này tận dụng `shared-foundations` `AppEnvironment.fake()` + `URLProtocol` stub + `KeychainStore` fake đã dựng sẵn, các test target `calo-ai-testTests` + `Calo-AIUITests` đã có từ `project-structure`. KHÔNG bao gồm feature mới, tối ưu performance riêng (xem `performance-optimization`), hay đổi kiến trúc.

## Requirements

### Requirement 1 (REQ-001): End-to-End Core Loop Test
**User Story:** As a QA/release engineer, I want an automated end-to-end test that drives the "Camera permission grant → capture → AI mock → confirmation edit → save → diary shows entry" flow, so that I can guarantee the competitive differentiator (logging speed + accuracy workflow) does not regress before each release.
**Source:** FR-001 (camera permission), FR-002 (capture), FR-003 (AI result), FR-004–FR-008 (confirmation edit), FR-012 (diary), UC-001–UC-008, UC-011, PRD §9 (core loop <10s), §12 (scan completion rate)

#### Acceptance Criteria
1. AC-001.1: THE SYSTEM SHALL provide an XCUITest `CoreLoopE2ETests` that drives: grant camera permission → tap "Use This" on a fixture JPEG (≥640×480) → mock AI Vision response returns `{meal: "Pho", calories: 450, protein: 25g, carbs: 60g, fat: 12g, ingredients: [broth,noodles,beef], confidence: 88}` → on Confirmation tap 1 ingredient, change portion .medium → .large → tap Save → assert diary list shows the new entry with correct totals.
2. AC-001.2: WHEN the E2E test runs on iPhone 12+ simulator (iOS 16+) THEN THE SYSTEM SHALL complete the core loop (capture confirmation shown → diary entry visible) in <10 seconds (PRD §9 core-loop target, measured by XCUITest timestamps).
3. AC-001.3: THE SYSTEM SHALL stub the AI Vision endpoint via `URLProtocol` (`AIVisionStub`) and the image-picker via `PhotosPickerStub` so the test runs deterministically without hitting the network or the photo library.
4. AC-001.4: WHEN the test asserts the diary list THEN THE SYSTEM SHALL verify the entry appears, calories/macros match the mocked AI payload, and the `ScanQuotaService.used` increments by 1 only after Save (BR-009.4) — not on capture.
5. AC-001.5: IF camera permission is denied (mocked `denied` state) THEN THE SYSTEM SHALL drive the negative branch (settings deep-link state) and assert no Save occurs, no AI call is made, and `ScanQuotaService.used` is unchanged (error path coverage).

### Requirement 2 (REQ-002): Subscription Purchase Flow Test
**User Story:** As a release engineer, I want an automated StoreKit-sandbox-driven test for the paywall → trial start → subscription active → cancel → restore flow, so that I can guarantee we never repeat Cal AI's billing rejection (Guideline 3.1.2c/5.6) and free-to-paid conversion does not regress.
**Source:** FR-021 (paywall), FR-022 (trial start), FR-023 (subscription verify), FR-024 (cancel), FR-025 (manage subscription), FR-026 (restore), UC-019–UC-023, NFR-017 (3-scan/day free), NFR-018 (7-day trial auto-expiry), PRD §9 (StoreKit sandbox billing test), §13 (Apple rejection risk)

#### Acceptance Criteria
1. AC-002.1: THE SYSTEM SHALL provide an XCUITest `SubscriptionFlowTests` that drives: tap "Upgrade" on paywall (WF-006) → assert both monthly and annual price cards are visible with explicit cycle and price (no dark pattern — NFR-018, BR-022.4) → tap annual → StoreKit sandbox sheet opens → confirm with `test_sign` credentials → assert "Premium activated" toast and `SubscriptionStatus` becomes `active` in `SubscriptionRepository`.
2. AC-002.2: WHEN the trial is started THEN THE SYSTEM SHALL assert `trial_start_date = today`, `trial_end_date = +7 days`, and the free-tier scan badge on Camera tab switches from "X/3" to "Unlimited" (NFR-017/018, FR-009).
3. AC-002.3: THE SYSTEM SHALL provide `RestorePurchaseTests` that, after logging in with a second sandbox Apple ID that has a prior receipt, taps "Restore purchases" on Settings (WF-007) and asserts the previously-entitled Premium status is re-asserted in `SubscriptionRepository` (FR-026, AC-026.x).
4. AC-002.4: THE SYSTEM SHALL provide `CancelFlowTests` that, from an active subscription, opens WF-018 cancel modal → taps "Continue cancel" → deep-links to App Store subscription page (verified by URL host containing `apps.apple.com`) and, after returning, asserts local subscription status reflects `pendingCancellation` per BR-024.1.
5. AC-002.5: IF the StoreKit sandbox sheet is cancelled mid-purchase THEN THE SYSTEM SHALL assert no `SubscriptionRepository` mutation occurs, no `paywall_viewed → subscription_started` analytics gap is created, and the paywall is shown again without "ghost" trial state (negative branch — prevents ERR-022.1).

### Requirement 3 (REQ-003): Unit Test Coverage Audit (Core Business Logic)
**User Story:** As an iOS tech lead, I want a CI-enforced coverage gate of ≥60% on core Services and ViewModels, so that quality of business logic does not silently decay with each spec and we satisfy NFR-SF-006 / Overview §5 Phase 3 commitment.
**Source:** NFR-SF-006 (≥60% on Services + Models), Overview §5 (Phase 3 "unit tests target 60% coverage core logic"), §6.1 (same); covers all FR-001..FR-026 across `camera-capture`, `ai-recognition`, `confirmation-edit`, `diary-logging`, `dashboard-view`, `paywall-display`, `subscription-management`, `authentication`, `onboarding-form`, `account-management`, `subscription-settings`, `settings-management`

#### Acceptance Criteria
1. AC-003.1: THE SYSTEM SHALL produce an xcode-generated code-coverage report (`xcodebuild test -enableCodeCoverage YES`) and a derived `xccov` summary over `Shared/Services/**`, `Shared/Models/**`, and every `Features/<F>/ViewModels/**` and `Features/<F>/Services/**` directory (the "core business logic" set defined by `ios-architecture`).
2. AC-003.2: WHEN the coverage script runs in CI THEN THE SYSTEM SHALL fail the build if the line-coverage on the core business logic set is <60% (NFR-SF-006). The threshold SHALL be enforced via a `coverage-gate.sh` script invoked from XcodeBuildMCP `test_sim`.
3. AC-003.3: THE SYSTEM SHALL include per-spec coverage maps under `Tests/Coverage/<SpecName>.md` listing every ViewModel/Service, its coverage %, and any function below 60% with a justification (e.g., "wraps AVFoundation — covered by integration test"). Maps SHALL be regenerated each `test_sim` run.
4. AC-003.4: IF a NEW file under `Features/<F>/ViewModels/` or `Features/<F>/Services/` is added in a phase 3–8 spec without at least one unit test THEN THE SYSTEM SHALL flag it as "untested new business logic" in the coverage map and the build SHALL fail the coverage gate (prevents silent decay; matches NFR-SF-006).

### Requirement 4 (REQ-004): App Store Submission Prep (Metadata + Privacy Nutrition Label)
**User Story:** As the product/ASO owner, I want a complete App Store Connect submission package — metadata, localized descriptions, screenshot set for all required device classes, and a Privacy Nutrition Label that matches the data the app actually collects — so that the submission does not get rejected for inaccurate declarations (PRD §9, §13) and we honor the "transparent billing + privacy" positioning (PRD §1, §4).
**Source:** PRD §9 (Privacy Policy, Privacy Nutrition Label, StoreKit sandbox billing test), §11 (pricing $9.99/mo, $39.99–49.99/yr, 7-day trial), §13 (Apple rejection risk for Guideline 3.1.2c/5.6; rủi ro khai báo sai), Overview §5 Phase 3 (Privacy Policy + App Store metadata), Overview §3.1 (RevenueCat + Superwall, Supabase + RLS)

#### Acceptance Criteria
1. AC-004.1: THE SYSTEM SHALL ship a `StoreMetadata/app-store-metadata.yaml` (or `.json`) containing: app name, subtitle, primary category, secondary category, keywords (≤100 chars), support URL, marketing URL, privacy policy URL, localized `description` (EN + VI) and `whats_new` — versioned per release.
2. AC-004.2: THE SYSTEM SHALL provide a `StoreMetadata/screenshots/` set covering iPhone 6.7" (iPhone 14 Pro Max), iPhone 6.1" (iPhone 14), iPhone 5.5" (iPhone 8 Plus), and iPad 12.9" if iPad-targeted — at minimum: 3 screenshots per device class for the "first three" set (App Store requirement), each labeled `<DeviceClass>-<ScreenName>-<Locale>.png`.
3. AC-004.3: THE SYSTEM SHALL provide a `PrivacyNutritionLabel.md` declaring exact data types per Apple's categories: Photos/Food Images (used for AI inference, linked to user, not used for tracking), Health & Fitness (meal logs + weight + calorie goal, linked to user, not used for tracking), Identifiers (Apple ID user ID, linked), Usage Data (analytics, linked), Diagnostics (crash reports + perf, linked); and "Data Not Collected" entries for any category not used. The label SHALL match what `shared-foundations` `AuthService`, `DataClient`, `OfflineSyncService`, Firebase Crashlytics, Firebase Analytics, and RevenueCat actually transmit.
4. AC-004.4: THE SYSTEM SHALL ship a `PrivacyPolicy.md` (linked from app + App Store Connect URL) covering: data collected, purpose, retention (PRD §9 auto-delete ảnh sau 7 ngày trừ khi user archive), user rights (export + delete per PRD §9), contact, GDPR/CCPA delete request SLA (30 ngày per Overview §8 risk table).
5. AC-004.5: IF any of metadata / screenshots / Privacy Nutrition Label / Privacy Policy is missing THEN THE SYSTEM SHALL fail the App Store submission readiness gate (`scripts/appstore_readiness_check.sh`) — prevents incomplete submission per PRD §9 "Mức độ Sẵn sàng Phát hành" (release-blocker).

### Requirement 5 (REQ-005): Crash-Free Verification (≥99%)
**User Story:** As a release engineer, I want a verified crash-free rate ≥99% on the TestFlight beta build before promoting to public release, so that we satisfy the reliability bar (PRD §9 / NFR-015 / Overview §6.1) and do not lose user trust the way Cal AI did post-breach.
**Source:** PRD §9 (Crash-free sessions ≥99.5%), NFR-015 (Crash-Free Rate <0.1% crash), Overview §6.1 (Crash-free ≥99%), §3.1 (Firebase Crashlytics), Phase 4 Launch & Early Monitoring

#### Acceptance Criteria
1. AC-005.1: THE SYSTEM SHALL ship a `Tools/CrashMonitor/CrashlyticsVerifier.swift` (and the matching Android-irrelevant iOS hook in `App/AppDelegate.swift`) that confirms `FirebaseApp.configure()` ran and Crashlytics collection was enabled (no consent dialog blocks collection) — verified by a `test_app_initialization_smoke` UI test.
2. AC-005.2: THE SYSTEM SHALL run a TestFlight beta for ≥7 days with ≥30 external testers, then export a `CrashlyticsReport.md` showing: total sessions, crash count, crash-free rate, top-3 crash signatures with stack traces, and any ANR/non-fatal signal. Crash-free rate SHALL be ≥99% to pass (Overview §6.1); 99.0%–99.5% triggers a conditional pass requiring an explicit `PO + iOS Lead` sign-off note.
3. AC-005.3: THE SYSTEM SHALL auto-emit `analytics_event("app_crash")` with the `fatal` flag in every `AppError` catch path that originated from a `fatalError`/`preconditionFailure` redirect (via a `CrashMonitor.recordNonFatal(_:)` hook in `ErrorHandler`) so non-fatal errors show up in Crashlytics even when they were caught by retry.
4. AC-005.4: IF a regression drops crash-free rate below 99% during beta THEN THE SYSTEM SHALL block the public release promotion until the top crash signature is fixed or explicitly waived in `ReleaseSignOff.md` (release-blocker gate).

## Non-Functional Requirements
- NFR-TI-001: Test reliability — E2E + integration tests SHALL be deterministic (no network, no real photo library, no live StoreKit outside sandbox) and SHALL pass ≥95% of 10 consecutive runs on a clean sim (per CI parity). Measured: `xcodebuild test -resultBundlePath` flake rate.
- NFR-TI-002: Coverage gating — Code-coverage gate SHALL fail the build if any of (a) core-business-logic <60%, (b) a new ViewModel/Service has 0 tests (NFR-SF-006). Measured by `coverage-gate.sh`.
- NFR-TI-003: Billing safety — Subscription flow tests SHALL be run on StoreKit 2 sandbox configuration with `test_sign` credentials and SHALL be re-run before every App Store submission (PRD §9 "luồng billing phải được test đầy đủ trong StoreKit sandbox"). Measured: `SubscriptionFlowTests` green before `appstore_readiness_check.sh` passes.
- NFR-TI-004: Crash-free release gate — Public release SHALL be blocked unless `CrashlyticsReport.md` for the prior TestFlight cycle shows ≥99% crash-free (NFR-015). Measured: `release_signoff_check.sh` reading the report.
- NFR-TI-005: Submission readiness — `appstore_readiness_check.sh` SHALL fail if any of (metadata yaml, screenshot set ≥3 per device class, Privacy Nutrition Label md, Privacy Policy md) is missing (PRD §9 "Mức độ Sẵn sàng Phát hành"). Measured: zero missing artifact.
